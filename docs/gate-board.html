Right now

v1.4.1 is public, and today it produced the fork's first in-the-wild installer defect. Upgrading on this machine failed with Error opening file for writing: …\sona.exe — two orphaned sona.exe processes from an earlier run still held locks on the install directory. The stock Tauri NSIS template closes only the main executable before installing and knows nothing about sidecars, so any Sona process that outlives an app crash blocks every future upgrade. The processes were killed by hand and the install completed. Fixed at the source in 6a980de: pre-install and pre-uninstall hooks now taskkill sona.exe before any file is touched (windows/hooks.nsh), the pre-existing vc_redist logic was merged into that same file (Tauri accepts one hooks file per build), and tauri.windows.conf.json — a cross-platform leftover whose own installerHooks entry silently overrode the main config — was merged into tauri.conf.json and deleted. The fix is now proven in a real install (2026-08-26, recorded in RELEASING.md): a detached sona.exe serve was spawned from the install directory to hold the lock — the exact condition that produced the file-write error — and the hooks-bearing locally built installer ran silently to exit code 0, killed the orphan, and rewrote the install directory. The published artifact was then restored by re-downloading the GitHub asset (hash a86b6bba…, exact match) and reinstalling it; the installed vibe.exe re-hashed to 37186b76…, byte-identical to the published record. The published v1.4.1 installer still lacks the hook — it first ships in the next release. A correction to the previous refresh: it claimed the build tree had been removed; that observation was wrong (it checked the wrong directory — the tree and the hooks installer were still present, which is what made today's test cheap). cargo clean has now actually been run.

The gate is unchanged at 2 of 6, the weakest of any published release. What cannot be proven from this machine without the owner: criteria 3, 5 and 6 need a dictating voice, criterion 4 needs one elevated shell to create the firewall rules.

Two contradictions stand. First, the standing one: RELEASING.md opens by stating every release re-runs the full verification, yet the published v1.4.1 artifact ran two of six criteria. Second, found today while consolidating the hooks: the installer itself can reach the network — the inherited vc_redist section downloads vc_redist.x64.exe from aka.ms during installation whenever the VC++ runtime is missing. RELEASING.md's zero-egress audit covers the app binary and its runtime sockets, not the installer's own network behaviour, so this has shipped unexamined in every release to date. It is now documented in a warning comment in windows/hooks.nsh, but no controlled document rules on it. The third contradiction from the last refresh — origin on HTTPS despite the recorded SSH switch — is resolved: root cause found and fixed, SSH restored (see activity).
