Right now

v1.4.1 is public, its record now says so, and on 2026-08-26 it produced the fork's first in-the-wild installer defect. Upgrading on [B] failed with Error opening file for writing: …\sona.exe — two orphaned sona.exe processes from an earlier run still held locks on the install directory. The stock Tauri NSIS template closes only the main executable before installing and knows nothing about sidecars, so any Sona process that outlives an app crash blocks every future upgrade. The processes were killed by hand and the install completed. Fixed at the source in 6a980de: pre-install and pre-uninstall hooks now taskkill sona.exe before any file is touched (windows/hooks.nsh), the pre-existing vc_redist logic was merged into that same file (Tauri accepts one hooks file per build), and tauri.windows.conf.json — a cross-platform leftover whose own installerHooks entry silently overrode the main config — was merged into tauri.conf.json and deleted. The fix is proven in a real install on [B] (2026-08-26, recorded in RELEASING.md): a detached sona.exe serve was spawned from the install directory to hold the lock — the exact condition that produced the file-write error — and the hooks-bearing locally built installer ran silently to exit code 0, killed the orphan, and rewrote the install directory. The published artifact was then restored on [B] by re-downloading the GitHub asset (hash a86b6bba…, exact match) and reinstalling it; the installed vibe.exe re-hashed to 37186b76…, byte-identical to the published record. The published v1.4.1 installer still lacks the hook — it first ships in the next release. Separately, as of 2026-09-03 the v1.4.1 release notes carry the same partial-gate disclosure that the v1.3.0 and v1.4.0 notes carry, and name the installer by the dotted filename GitHub actually serves; RELEASING.md's v1.4.1 record, which had still said "Not published", now states the 2026-08-25 publication and the owner's 2-of-6 ruling.

The gate is unchanged at 2 of 6, the weakest of any published release. Criteria 1 (strings audit on both exes) and 2 (NSIS /S install with the quoted HKCU Run entry) passed on [A] 2026-08-25. What cannot be proven from either machine without the owner: criteria 3, 4, 5 and 6 — all four. Criteria 3, 5 and 6 need a dictating voice; criterion 4 needs one elevated shell to create the firewall rules. Both machines hold the same installed v1.4.1 bytes (37186b76…, hashed on each), so the four can be closed from either.

Three contradictions stand. First, the standing one: RELEASING.md opens by stating every release re-runs the full verification, yet the published v1.4.1 artifact ran two of six criteria — the third consecutive release to rest its runtime zero-egress proof on the strings audit and compile-time deletions alone. Since 2026-09-03 the public notes say so, though the disclosure sits under a first paragraph that still reads "Nothing leaves the machine.", the very claim criteria 3 to 6 exist to prove. Second, found 2026-08-26 while consolidating the hooks: the installer itself can reach the network — the inherited vc_redist section downloads vc_redist.x64.exe from aka.ms during installation whenever the VC++ runtime is missing. RELEASING.md's zero-egress audit covers the app binary and its runtime sockets, not the installer's own network behaviour, so this has shipped unexamined in every release to date. It is now documented in a warning comment in windows/hooks.nsh, but no controlled document rules on it. Third, new with this refresh: the two machines disagree about the world. The 2026-08-26 refresh from [B] retired the stale-sibling-clone item because the clone "no longer exists", and stated the machine's only key pair is ~/.ssh/id_ed25519_vps; on [A] the sibling clone is still present and A holds two key pairs, neither by that name. Both statements were true where they were made — the board was written as if there were one machine. Resolved since the last refresh: RELEASING.md's v1.4.1 record no longer contradicts the Releases page.
